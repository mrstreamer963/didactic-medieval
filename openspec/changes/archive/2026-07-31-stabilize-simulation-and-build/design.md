## Context

Текущий прототип разделяет ответственность между Rust/WASM-ядром и PixiJS-фронтендом: Rust хранит ECS-состояние, карту, маршруты, потребности и очередь строительства, а фронтенд управляет кадрами, вводом и отображением. Пауза сейчас реализована внутри кадра рендеринга, начальные объекты создаются случайными попытками, а часть проверок валидности находится только внутри отдельных веток логики.

## Goals / Non-Goals

**Goals:**

- Сделать один источник истины для состояния симуляции и гарантировать, что пауза не вызывает ECS.
- Централизовать правила валидности строительства и начальной генерации.
- Гарантировать выбор доступных объектов относительно конкретного юнита.
- Убрать маршруты, которые обходят A* и могут пересекать препятствия.
- Сделать стандартную сборку независимой от интерактивной установки необязательного оптимизатора.
- Добавить тестируемые контракты для каждого исправленного сценария.

**Non-Goals:**

- Новые типы зданий, ресурсов или потребностей.
- Изменение публичной формы WASM JSON API.
- Переписывание PixiJS-рендерера или смена ECS-фреймворка.
- Оптимизация производительности A* за пределами необходимого устранения fallback-маршрутов.

## Decisions

### 1. Пауза контролируется до вызова WASM

При `gameSpeed === 0` ticker обновляет только визуальное состояние, не вызывая `world.tick(0)`. Это сохраняет фактическое состояние мира неизменным и устраняет скрытые побочные эффекты систем, которые работают даже при нулевом delta.

Альтернатива — оставить `tick(0)` и сделать каждую ECS-систему pause-aware. Она требует дублировать проверку во всех системах и оставляет риск появления новых побочных эффектов, поэтому не выбирается.

### 2. Валидация строительства выполняется до создания объекта и job

`BuildRequest` принимается только если координаты находятся в карте, клетка проходима и `MapObjects` не содержит объект. Правило применяется одинаково к стене, кровати и кусту. Завершённая стена меняет проходимость только в момент завершения строительства; куст этого не делает.

### 3. Начальные кусты выбираются через уникальный набор клеток

Генерация повторяет выбор до тех пор, пока не будет размещено ровно три куста, либо использует заранее перемешанный список проходимых клеток. Предпочтителен второй вариант: он гарантирует уникальность и не зависит от вероятности коллизий.

### 4. Поиск потребности получает позицию юнита

Логика выбора объекта принимает текущую позицию юнита и сравнивает квадрат евклидова расстояния до каждого подходящего объекта. Это сохраняет простоту текущей модели и устраняет выбор объекта относительно начала координат.

### 5. Все wandering-маршруты проходят через A*

Инициализация юнита и повторное назначение цели используют один валидированный механизм поиска пути. При недостижимой цели она отбрасывается; прямой fallback запрещён. Если подходящая цель не найдена за ограниченное число попыток, путь остаётся прежним или пустым до следующего безопасного назначения, но юнит не пересекает препятствия.

### 6. WASM-сборка по умолчанию использует no-opt

Основной npm-скрипт должен работать без скачивания бинарника `wasm-opt`. Оптимизация может быть отдельным явно документированным профилем или локальной командой. Это делает CI и локальную разработку предсказуемыми на платформах, где wasm-pack не может подобрать prebuilt optimizer.

### 7. Тесты сначала на уровне Rust, затем на границе фронтенда

Инварианты карты, генерации, строительства, потребностей и маршрутов проверяются Rust-тестами. Для UI добавляются тесты поведения паузы и преобразования входного состояния только там, где это возможно без запуска полноценного браузера.

## Risks / Trade-offs

- [Risk] При отсутствии reachable-цели юнит может временно остановиться. → Сохранять предыдущий маршрут и повторять поиск на следующем событии/цикле, не используя небезопасный прямой путь.
- [Risk] No-opt WASM может быть больше оптимизированного. → Оставить отдельную release-команду с `wasm-opt` для production-пайплайна.
- [Risk] Увеличение числа Rust-тестов усложнит поддержку. → Тестировать публичные инварианты и сценарии, не внутреннюю структуру ECS.
- [Risk] Согласование старых спецификаций может выявить дополнительные расхождения. → В рамках change исправлять только перечисленные capability-контракты; остальные проблемы вынести в отдельный change.

## Migration Plan

1. Обновить npm-команды и документацию путей crate.
2. Внести изменения в Rust-валидацию, генерацию и pathfinding.
3. Изменить pause-ветку фронтенда.
4. Запустить Rust/TypeScript-тесты и production-сборку.
5. Проверить чистоту `openspec/changes/archive/` и валидировать новый change.

Откат выполняется удалением или отменой коммитов только нового change; архивные артефакты и публичные имена API не затрагиваются.
